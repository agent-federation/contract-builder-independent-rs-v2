# PAP v0.1 — Independent Verifier
## Phase 2a — Minimal Standalone Verifier

**Status:** EXECUTION BRIEF
**Phase:** Phase 2a — Minimal Standalone Verifier
**Specification:** Portable Assurance Package (PAP) v0.1
**Purpose:** Independent implementation for the Phase 3 interoperability experiment.

---

## 0. Implementation configuration

```text
IMPLEMENTATION_LANGUAGE = "rust"
```

This is the only language-specific configuration value in this brief.

The implementation must be written natively in the selected language. Do not translate or port code from another implementation.

The implementation language, runtime, dependencies, architecture, module structure, error model and test framework are implementation decisions.

## 1. Objective

Implement a minimal, independently developed PAP v0.1 verifier corresponding exactly to **Phase 2a in RFC §14**.

The goal is to establish an independently implemented and testable foundation for PAP verification.

This phase covers:

- directory traversal and package filesystem access;
- strict manifest parsing and schema validation;
- JCS canonicalization;
- PAP digest algorithms and package-derived identities;
- report construction;
- verdict and exit-code foundations;
- parsing, digest and package-safety behavior required by the Phase 2a acceptance boundary.

This is a working implementation phase, not a specification-analysis-only exercise.

The expected result is executable software with an independent test suite, reproducible verification evidence and documented limitations.

Do not implement later phases merely to make the verifier appear more complete.

---

## 2. Independence requirements

This is a blind independent implementation.

The implementation must be developed without access to:

- the original Contract Builder verifier source;
- the original verifier tests, test helpers or internal utilities;
- the Python independent verifier source;
- tests or test results from either implementation;
- previous implementation reports or audit findings;
- previous implementation plans, traceability matrices or architectural descriptions;
- implementation PR discussions, reviews or commit history;
- outputs generated by either implementation.

Do not inspect, copy, translate, reconstruct or infer internal implementation architecture from another verifier.

Do not use another implementation as an oracle.

The only authoritative behavioral source is the approved PAP v0.1 normative material supplied in the frozen input bundle.

A different language is preferred by RFC §13.4, but independence is primarily a property of the development process and codebase, not the language alone.

## 4. Phase 2a functional scope

### 4.1 Package directory handling

Implement the directory-only PAP package reader.

It must:

- recognize the package root;
- locate and read `assurance-package.json`;
- enforce the normative package path grammar;
- validate declared package paths before filesystem access;
- enforce root confinement;
- reject invalid, duplicate and case-colliding paths as specified;
- reject symlinks and non-regular files as required;
- resolve a `PACKAGE` argument that is a symbolic link to a directory once and use the resolved
  directory as the package root; symbolic links at or below a declared payload path remain
  rejected (RFC §4.3.2, §9.2);
- report an undeclared-file scan that cannot complete as the RFC §4.3.3 scan-incomplete
  condition (`pap.package.undeclared-scan-incomplete`, `coverage.full: false`), never as a pass;
- distinguish missing declared files from permitted undeclared files;
- enforce applicable package and filesystem resource limits;
- avoid following paths outside the package root;
- handle malformed or inaccessible filesystem entries without silently treating them as absent.

Do not implement archive, ZIP, TAR or OCI transport.

### 4.2 Manifest parsing and validation

Implement strict manifest parsing according to RFC §4 and Appendix A.

Requirements include:

- UTF-8 validation;
- BOM rejection;
- duplicate JSON key rejection;
- strict I-JSON handling;
- integer-only JSON number semantics where specified;
- nesting and string-size limits;
- closed schema validation;
- required fields, types, patterns and enums;
- cross-field invariants;
- duplicate identifier and path detection;
- version and compatibility validation;
- extension and required-feature parsing.

Do not rely on permissive parser defaults.

In particular, a parser that silently accepts duplicate keys using last-value-wins semantics is not acceptable.

### 4.3 JCS canonicalization

Implement RFC 8785 JSON Canonicalization Scheme behavior as required by PAP.

Validate the implementation against every applicable Appendix E vector.

Do not assume a third-party JCS library is conformant merely because it advertises RFC 8785 support.

A library may be used if the independent tests demonstrate exact agreement with the normative vectors.

### 4.4 Digest algorithms and identities

Implement the normative PAP digest primitives and identity calculations.

This includes the applicable:

- domain-separated SHA-256 functions;
- framing algorithm;
- canonical manifest digest;
- package identity;
- artifact digests;
- raw source digests;
- normalized input digests;
- claim-file digests;
- extension closure identity;
- other package-derived identities explicitly required by Appendix E and the Phase 2a boundary.

Requirements:

- exact domain strings;
- exact byte encoding;
- exact framing and length-prefix semantics;
- correct UTF-8 handling;
- correct LF normalization and binary fallback;
- no accidental string-based digest comparison where byte-level identity is required.

Every applicable Appendix E vector must pass.

Do not implement cryptographic signature verification or signer trust in this phase.

### 4.4.1 Checker identity

Phase 2a MUST compute and report the verifier's own checker identity. This is the
`implementationDigest` and `checkerIdentity` construction of RFC §5.8; it is not a
package-derived identity and MUST NOT be copied from package data.

```text
implementationDigest = extensionClosureDigest(kind="checker", id=<verifier-id>,
                                              version=<verifier-version>,
                                              files=<closure-files>,
                                              dependencies=<pinned-dependencies>)
checkerIdentity      = H("pap.checker.identity.v1",
                         JCS({"id": <verifier-id>, "version": <verifier-version>,
                              "implementationDigest": implementationDigest}))
```

- `<verifier-id>` is `pap.verifier.<language>`; `<verifier-version>` is `0.1.0`. The same
  values MUST appear in `verifier.id`/`verifier.version` in every report and in every check
  record's `checker` object.
- `files` is the implementation's own source closure: every tracked text file that contributes
  to building the verifier, with repo-relative POSIX paths sorted in ascending UTF-8 byte
  order. Include source, build manifests and lockfiles. Exclude tests, fixtures, documentation
  and generated files that are not build inputs. Normalize text per RFC §5.2 (UTF-8;
  CRLF/CR → LF); a binary file in the closure is an error.
- `dependencies` is the complete pinned third-party dependency closure declared by the
  implementation's lockfile/build manifest: one `(name, version, integrity)` record per package,
  sorted by name then version, with `integrity` copied verbatim from the lockfile for the artifact
  the build actually consumes (for example a Cargo checksum, a Go module `h1:` value, or the
  selected wheel/sdist hash). A lockfile may carry several integrity values for one package
  (`uv.lock` per-wheel/sdist hashes; `go.sum` module and `/go.mod` lines); the record is one per
  package, generated metadata such as `/go.mod` lines and unselected wheels are not separate
  dependencies, and the selected artifact is recorded in the experiment record's `artifact` field
  (outside the hash). The selection rule
  must be deterministic for the implementation. The language runtime and standard library are
  not dependency records; record the compiler/runtime name and version in the experiment record.
- Compute the closure at build or run time from the bytes present in the implementation
  checkout. Never copy a digest from package data, a previous run, another implementation or
  the reference verifier.
- Appendix E.3 is the normative checker-identity vector. Reproduce both its
  `implementationDigest` and `checkerIdentity` values exactly.
- Self-check, both directions, with the commands and before/after digests recorded:
  (a) change one byte of one included file; rebuild if the implementation has a build step,
  otherwise re-run, and recompute — the digest MUST change;
  (b) change a file outside the closure; rebuild/re-run and recompute — the digest MUST NOT
  change.

### 4.5 Report construction

Implement the Phase 2a report foundation using Appendix C.

The implementation must:

- produce a structurally valid report for supported execution paths;
- represent dimensions and statuses without conflating them;
- preserve the distinction between verdict and coverage;
- distinguish `NOT_EVALUATED`, `UNAVAILABLE`, `UNSUPPORTED` and other normative states;
- report package-derived identities correctly;
- represent diagnostics and limitations according to the schema;
- avoid inventing successful check results.

The report's `verifier` object MUST contain `id`, `version`, `implementationDigest` and
`checkerIdentities[]`. The array MUST contain exactly one element for a one-binary
implementation, and that element MUST equal `identities.checkerIdentity`.

A report must never imply that a required check passed when that check was not evaluated.

Where later-phase checks are not implemented, their absence must not produce a false `PASS`.

### 4.6 Verdict and exit-code foundations

Implement the normative verdict precedence and exit-code mapping needed by the Phase 2a report foundation.

The mapping must follow the RFC, not a language-specific exception convention.

Keep these concepts separate:

- package parsing and integrity;
- check evaluation;
- coverage;
- verdict;
- process exit status.

A process exit code must not replace the report as the authoritative description of what was evaluated.

### 4.7 Execution interface

Provide the smallest executable interface necessary to run the Phase 2a verifier and its tests.

Do not implement the full public CLI contract of Phase 2c.

In particular, `inspect`, `explain`, trust-policy options and text/JSON CLI presentation are outside this phase unless a minimal internal interface is strictly necessary for Phase 2a testing.

Document any temporary execution interface clearly.

## 5. Explicitly out of scope

The following are not Phase 2a deliverables.

### Phase 2b

Do not implement the three PAP checks:

- `pap.check.digest-integrity/1`;
- `pap.check.source-quote/1`;
- `pap.check.relation-consistency/1`.

Do not implement their check-specific witnesses or full check execution semantics.

Implementing digest primitives and package-derived identities does not authorize implementing the digest-integrity check.

### Phase 2c

Do not implement the complete CLI contract:

- `verify`;
- `inspect`;
- `explain`;
- full text output;
- full JSON CLI stream behavior;
- trust-policy parsing and evaluation.

### Phase 2d

Do not implement:

- DSSE;
- PAE;
- Ed25519;
- signature envelope discovery;
- signer identity and authorization;
- trust policy;
- checker/profile recognition.

### Other exclusions

Do not implement:

- in-toto integration;
- producer integration;
- Contract Builder integration;
- Markdown rendering;
- package-supplied code execution;
- network access;
- archive transport;
- online revocation;
- a producer-side package generator.

Do not expand the normative specification.

## 6. Security requirements

Treat every package as hostile input.

The verifier must:

- perform no network access;
- never execute package content;
- never import or evaluate package-supplied code;
- never invoke producer tooling;
- validate paths before opening files;
- enforce resource limits while reading;
- avoid unbounded directory enumeration;
- avoid unbounded buffering;
- fail closed on malformed or ambiguous input;
- never turn a resource-limit failure into a successful verification result;
- never silently ignore a filesystem error that affects the evaluated scope.

Use safe filesystem APIs and language-native resource management.

Document platform-specific limitations rather than claiming stronger guarantees than the implementation provides.

The implementation must not use a weaker security policy merely because the selected language or standard library makes the normative behavior inconvenient.

## 7. Testing requirements

Create a completely independent test suite.

Do not reuse another implementation's test code, test framework helpers or expected-output files.

### 7.1 Appendix E

All applicable Appendix E vectors must pass.

Include tests for:

- canonical manifest bytes;
- package identity;
- domain-separated digests;
- framing ambiguity;
- LF normalization;
- source and input digest calculations;
- quote-related digest primitives where applicable to the Phase 2a boundary;
- identity-form exclusions and record identity where required by the Phase 2a specification.
- checker identity: Appendix E.3, plus the two-way closure self-check.

### 7.2 Parsing and schema tests

Test:

- valid manifest;
- invalid JSON;
- invalid UTF-8;
- BOM;
- duplicate keys;
- non-integer number tokens;
- unknown core fields;
- missing required fields;
- invalid enums and patterns;
- duplicate IDs;
- duplicate paths;
- invalid cross-field relationships;
- unsupported versions.

### 7.3 Package-safety tests

Test the applicable normative safety cases, including:

- path traversal;
- absolute and invalid paths;
- symlink handling;
- non-regular files;
- duplicate and case-colliding paths;
- missing declared files;
- undeclared files;
- absent manifest;
- malformed manifest;
- manifest and JSON resource limits;
- payload resource limits;
- bounded directory traversal;
- root confinement.

### 7.4 Phase boundary discipline

The RFC §12 corpus includes cases belonging to later phases.

Do not silently claim that all F01–F61 cases are Phase 2a acceptance tests.

For every case considered in Phase 1, document:

- which Phase 2a behavior it tests;
- which assertions are applicable now;
- which assertions depend on Phase 2b, 2c or 2d;
- whether the complete case can be executed in Phase 1;
- why an assertion is deferred if it cannot be evaluated yet.

Do not weaken normative expectations to make the implementation pass.

If the exact Phase 2a case subset is ambiguous, record the ambiguity and request maintainer clarification.

The Phase 2a comparison scope is published as
`pap/fixtures/pap-v0.1/cases-phase2a.json`. It is experiment metadata, not an amendment to RFC
§12: `cases.json` remains the normative corpus. Use the case set to select the cases and fields
a Phase 2a verifier must match; record any case it excludes as later-phase and do not claim it
as Phase 2a acceptance.

## 8. Architecture and implementation freedom

The implementation architecture is entirely independent.

Choose the design that best supports:

- correctness;
- explicit failure states;
- safe filesystem access;
- bounded resource use;
- deterministic output;
- maintainability;
- testability.

You may use standard language libraries and third-party dependencies.

For every dependency, record:

- name and version;
- purpose;
- whether it affects parsing, canonicalization, hashing or filesystem safety;
- relevant limitations;
- how conformance is established.

Do not imitate the module structure or internal abstractions of another implementation.

Do not add speculative abstractions for later phases unless they are necessary for the Phase 2a design.

## 11. Stop conditions and escalation

Stop and request maintainer clarification when:

- normative sources conflict;
- an expected behavior cannot be derived from the RFC;
- a fixture appears inconsistent with the RFC;
- a required security property cannot be implemented with the available input contract;
- a resource limit or error state is underspecified;
- a proposed interpretation would change normative behavior.

Do not resolve normative ambiguity by copying another implementation.

Do not silently amend schemas, fixtures, RFC text or owner decisions.

A specification defect is a specification issue, not permission to invent implementation behavior.

---

## 12. Completion criteria

Phase 1 is complete only when:

- the Phase 2a functionality described in RFC §14 is implemented;
- applicable Appendix E vectors pass;
- the agreed parsing, digest and safety cases of §12 pass;
- report and exit-code foundations follow the normative contract;
- no required unevaluated scope can yield a false `PASS`;
- independent tests are reproducible;
- all unresolved issues are explicitly recorded;
- the frozen normative input bundle remains unchanged;
- the implementation is committed and its final state is reproducible.

Phase 1 completion does not establish:

- Phase 2b completion;
- full PAP v0.1 conformance;
- Tier A or Tier B conformance;
- Gate 3 completion;
- interoperability with another verifier;
- semantic truth or legal enforceability.

The result is a standalone Phase 2a implementation ready for a separately authorized review and subsequent phase work.

Work only from the authorized normative input bundle.

Build your own understanding of the specification, your own architecture, your own implementation and your own tests.

The goal is not to reproduce an existing verifier.

The goal is to independently implement the same normative contract and produce enough evidence for a later, genuinely independent comparison.
